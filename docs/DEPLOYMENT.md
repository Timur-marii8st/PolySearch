# Серверный контур PolySearch

Эксплуатационный кандидат для **одной организации**, не мультиарендный SaaS. Несколько учётных записей работают с общим workspace и общими кампаниями. Все авторизованные роли могут читать и экспортировать данные; отдельная изоляция клиентов/проектов не реализована.

## Локальный режим

Существующий запуск SQLite без входа сохранён только для доверенного локального компьютера. Не публиковать его в сети. PostgreSQL требует POLYSEARCH_AUTH=required.

## Docker Compose (loopback)

```bash
umask 077
mkdir -p secrets
chmod 700 secrets
openssl rand -hex 32 > secrets/db_admin_password.txt
openssl rand -hex 32 > secrets/db_app_password.txt
# UID контейнера app должен читать только свой secret; настройте владельца/ACL.
chmod 644 secrets/db_admin_password.txt secrets/db_app_password.txt
docker compose up -d --build --wait
docker compose exec app python -m polysearch.admin user admin --role admin
```

Для этого локального Compose-примера права 644 у файлов нужны для чтения bind-mounted secrets разными UID внутри контейнеров; каталог secrets обязан оставаться закрытым (700). В контейнер приложения передаётся только пароль приложения. На сервере заказчика используйте менеджер секретов или отдельные ACL под UID процесса приложения и PostgreSQL. Не передавайте этот каталог третьим лицам. Контейнер приложения не root, база не публикует порт. PostgreSQL role polysearch_app — не superuser, владелец своей БД. Init выполняется только при пустом томе; изменение secret-файла не меняет пароль существующей роли. Вход: http://127.0.0.1:8000/login. По умолчанию compose доступен только на loopback и использует cookie без Secure для HTTP.

Для сетевого доступа необходим TLS reverse proxy, точный внешний POLYSEARCH_ORIGIN=https://... и POLYSEARCH_COOKIE_SECURE=1, ограничение доступа к прокси, доверенные хосты, лимиты тела и частоты запросов, отдельный security review. Публичный порт не открывать. При смене origin также согласовать порт и прокси. Один процесс приложения на первом пилоте; транзакционный advisory lock сериализует операции внутри одной БД, но это не нагрузочно проверенная горизонтальная архитектура.

## Роли

| Действие | admin | researcher | reviewer | viewer |
|---|---|---|---|---|
| Чтение, экспорт | да | да | да | да |
| Создание/сброс workspace | да | нет | нет | нет |
| Измерения, импорт, ML, создание кампании/плана | да | да | нет | нет |
| Активация, согласование, отмена, закрытие | да | нет | да | нет |
| Метрики | да | нет | нет | нет |

Управление учётными записями только через серверную CLI: `python -m polysearch.admin user NAME --role researcher`, `--replace` для смены пароля/роли, `disable NAME` для отключения. Изменения отзывают сессии пользователя. Пароли PBKDF2-HMAC-SHA256 (600000 итераций, случайная соль), случайные session tokens хранятся только как SHA256; срок 8 часов. Cookies HttpOnly/SameSite=Strict, Secure в TLS-режиме. Изменяющие запросы требуют X-PolySearch-Request: 1 и проверку Origin, если он передан. Лимит 12 попыток входа на IP за 5 минут (за proxy без доверенной конфигурации все запросы могут иметь один IP). Имена авторов действий пилота берутся из сессии, не из поля actor клиента. Это не ЭП, строгая сегрегация обязанностей для администратора не обеспечена. Swagger в защищённом режиме требует сессии; для POST нужен также защитный заголовок (использовать клиент API).

## Миграция и резервные копии

Остановить запись в старую SQLite, сделать её копию, не публиковать файл. Запустить `python -m polysearch.admin migrate-sqlite /path/to/copy.sqlite3` с DSN целевой PostgreSQL и серверными зависимостями. Переносятся payload рабочего пространства и кампании транзакционно, только в пустую целевую БД, без учётных записей и сессий. Проверить количество кампаний, отчёты, SHA снимков. Старая база сохраняется.

```bash
sh deploy/backup.sh
sh deploy/verify-backup.sh backups/<имя>.dump
```

Backup: pg_dump custom format, контроль SHA256 и проверка списка. Verify восстанавливает в отдельную временную БД и удаляет её после проверки; не перезаписывает рабочую. Для восстановления заказчика использовать отдельную БД, проверить данные/права, отозвать все сессии (`python -m polysearch.admin revoke-sessions`) и только затем переключать приложение. Backup содержит конфиденциальные данные и хеши учётных записей: шифрование, offsite, retention и регулярная проверка восстановления — ответственность эксплуатации.

## Наблюдаемость

/health — liveness, /ready — доступность БД, /metrics — Prometheus-compatible gauges количества записей workspace и кампаний (admin). Приложение формирует записи логов изменений actor/role/path/status без тел запросов; для промышленной эксплуатации требуется настроить уровень/обработчик логгера polysearch.access, централизованный сбор и retention. Полноценный внешний мониторинг, алерты, нагрузочные тесты, шифрование хранилища, SSO/MFA, управление жизненным циклом ключей и независимый security review остаются задачами перед эксплуатацией. 

## Подтверждённые проверки

Коммит [6d239c6](https://github.com/Timur-marii8st/PolySearch/commit/6d239c61d3203eb3d4cc5c66f4364d7fc9f49310).

- [Python CI](https://github.com/Timur-marii8st/PolySearch/actions/runs/45891541561): 57 пройденных тестов, 2 PostgreSQL-теста пропущены в обычной SQLite-матрице, 1 предупреждение на каждой из версий 3.11 и 3.12.
- [Server integration](https://github.com/Timur-marii8st/PolySearch/actions/runs/45891541612): 7 пройденных тестов PostgreSQL/безопасности, включая миграцию, конкурентное обновление, rollback, аутентификацию, роли, отзыв сессий, защитный заголовок и ограничение входа; 1 предупреждение.
- В том же Server integration собран и запущен Docker Compose, создан тестовый администратор, выполнены вход и запись проекта, создан pg_dump и выполнен pg_restore во временную БД с запросом количества строк workspace и кампаний. Это базовая проверка восстановления, а не полный disaster recovery и не испытание на данных заказчика.
- [Регрессионный браузерный сценарий](https://github.com/Timur-marii8st/PolySearch/actions/runs/45891541550) проверяет прежний локальный интерфейс. Полный отдельный браузерный сценарий с авторизованными пользователями и TLS остаётся задачей приёмки.

## Перед вводом в эксплуатацию

- [ ] Определить конкретного заказчика, сетевой контур и ответственную команду.
- [ ] Проверить TLS, доверенные Host/Origin, лимиты запросов и настройку прокси; провести независимую проверку безопасности.
- [ ] Ввести централизованные аудит и мониторинг, алерты и SLO; настроить ротацию секретов и регулярные backup/restore.
- [ ] Утвердить матрицу доступа, изоляцию проектов при необходимости, политику хранения и экспортов; оценить SSO/MFA.
- [ ] Провести нагрузочное тестирование, включая длительные расчёты и конкурентные записи. Глобальная транзакционная блокировка пока сериализует операции, в том числе чтение состояния и идентификацию сессии.
- [ ] Подтвердить эксплуатацию на реальном контуре, проверить реальные данные, согласовать методику и провести физический пилот. LIMS и подключение лабораторного оборудования — отдельные интеграции.
