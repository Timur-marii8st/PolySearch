# LIMS / ELN — контракт обмена PolySearch v1

Работает файловый обмен через JSON и API с оператором. Не реализованы прямые коннекторы к конкретным продуктам (Benchling, LabWare и др.), webhook, M2M service account, автоматический запуск установки, поддержка HL7 и лабораторная сертификация. Для каждого заказчика требуется сопоставление полей, единиц, идентификаторов и тестирование его адаптера.

## Поток

1. Утвердить протокол и план в /pilot. Активный утверждённый план можно экспортировать через /exchange либо GET /api/exchange/campaigns/{cid}/orders/{pid}. Не выдавать предложенные, отклонённые, завершённые планы.
2. Передать JSON в лабораторную систему согласованным локальным каналом. Это информационное задание, не машинная команда оборудованию.
3. После физической попытки подготовить JSON результата. Вставить реальные идентификаторы и фактические измерения с единицами, первичную ссылку/номер документа, статус, фактическую стоимость и время. Не заполнять отсутствующие данные нулями и не выдавать прогноз за факт.
4. Исследователь отправляет файл на проверку. Технолог сверяет первичный результат, принимает либо отклоняет. Сервер повторно проверяет актуальность плана, ревизию кампании, хеш, единицы, фактический ID и статус.
5. Принятие атомарно записывает измерение в кампанию и решение во входящий журнал. В результате сохраняется provenance; новый опыт учитывается в бюджете и отчёте. Отклонение входящего сообщения — не отклонение уже выполненной физической попытки; при реальном неуспехе корректно внести failed.

## Схема результата

Версия polysearch.lab.v1. Пример только структуры (не химический опыт; хеш, ID и observed_at нужно взять из реального задания/измерения):
```json
{
  "schema_version": "polysearch.lab.v1",
  "source_system": "customer-lims",
  "external_id": "unique-result-id",
  "campaign_id": "<campaign UUID>",
  "plan_id": "<approved plan UUID>",
  "work_order_sha256": "<64 lowercase hex characters>",
  "run_id": "<independent physical experiment ID>",
  "observed_at": "<timezone-aware ISO 8601 after approval>",
  "actual_parameters": {"x": {"value": 0.5, "unit": "a.u."}},
  "outcomes": {"y": {"value": 0.9, "unit": "a.u."}},
  "status": "completed",
  "evidence": "<reference to primary result>",
  "currency": "RUB",
  "cost_minor": 10000,
  "elapsed_minutes": 10
}
```
При failed причина обязательна; допустимы частичные outcomes. При отклонении фактических параметров от плана нужен deviation_note; запись не участвует в обучении/подтверждении, но учитывается в затратах. Единицы совпадают буквально (включая пустую строку для безразмерных факторов без единицы); преобразования выполняются и проверяются в адаптере заказчика. Стоимость — целое число сотых долей валюты, по текущему соглашению протокола; не использовать валюты с другим числом десятичных знаков без согласования.

## API

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | /api/exchange/campaigns/{cid}/orders/{pid} | Согласованное задание с хешем |
| GET | /api/exchange/inbox?campaign_id=...&limit=20&offset=0 | Журнал (пагинация) |
| GET | /api/exchange/inbox/{iid} | Запись |
| POST | /api/exchange/inbox | {actor, result}; проверить и поместить в pending |
| POST | /api/exchange/inbox/{iid}/review | {actor, expected_revision, decision: accept/reject, note} |

Использовать защищённый сеанс (cookie) и заголовок X-PolySearch-Request: 1 для POST. В серверном режиме имя берётся из сеанса, а не поля actor. Исследователь/admin загружают, reviewer/admin принимают/отклоняют; viewer не имеет доступа к журналу обмена, но сохраняет чтение кампаний и уже принятых результатов, как и раньше. Администратор может выполнить обе роли, а ручной ввод по-прежнему доступен исследователю. Это операторский контроль, не обязательная двухсторонняя ЭП. В локальном режиме доверенный оператор имеет все возможности.

## Повторные сообщения и конфликты

Пара (source_system, external_id) уникальна во всей базе организации. Тот же нормализованный JSON возвращает существующую запись, в том числе после решения; изменённое содержимое с тем же ID — 409. Новая исправленная запись требует нового ID и явного объяснения в первичной ссылке/протоколе; не перезаписывает факт. Для одного физического run_id в кампании допускается одно измерение. Два различных входящих сообщения могут быть pending для одного плана, но только первое корректное принятие может записать результат; остальные должны быть отклонены. Дубли не расходуют бюджет. Устаревший expected_revision, отменённый/завершённый план, несовпадающий хеш — 409. Неверная схема/единица/валюта/метка времени — 422. Хеш обеспечивает идентификацию контента, не подтверждает отправителя или достоверность измерения. Изменения рабочей БД и удаление данных требуют полномочий эксплуатации.

Результаты хранятся в integration_inbox той же SQLite/PostgreSQL. Включены в миграцию и backup. На данный момент фильтрация inbox выполняется в памяти (не рассчитана на крупный поток). Нет очереди повторных сетевых доставок; файлы загружаются оператором. Клиентские записи не публиковать в Git.

## Демо без оборудования

```bash
python -m pip install -e ".[dev]"
POLYSEARCH_AUTH=local python -m polysearch.lab_demo --out artifacts/lab-demo
```
Отдельная временная SQLite и генерируемые значения с явными пометками. Команда не обращается к пользовательской БД, не подключается к LIMS. Выходной каталог должен быть новым; содержит задания, результаты, кампанию и отчёт. Демонстрационный отчёт нельзя использовать как коммерческое доказательство экономии.
