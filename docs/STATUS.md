# Статус реализации

Источник — предоставленная техническая карта v0.1.0. Код предшествующей версии не перенесён, а результаты старых испытаний не воспроизведены здесь. На этапе 2 создана независимая реализация ядра; её фактические возможности и запуск описаны в [IMPLEMENTATION](IMPLEMENTATION.md). Данный файл сохраняет историческую спецификацию.

## Данные экспериментов

Статус по карте: частично

Этот слой превращает файлы и ручные записи в единый журнал экспериментов. В первой версии работает универсальный CSV-импорт; для первого научного сценария выберем один мономер из Monash и сначала будем прогнозировать конверсию.

**Описанные функции:**
- Импорт CSV по именам факторов и свойств из конфигурации.
- Каждая завершённая запись обязана содержать все целевые свойства.
- Импорт всего файла атомарный: одна ошибочная строка отменяет запись всей партии.
- Экспорт CSV и снимка проекта JSON.

**Следующие задачи:**
- ETL Monash для одного мономера: температура, CT/CM и время пребывания → конверсия.
- Сохранение исходного experiment_id, единиц, протокола, источника, версии данных.
- Согласование измерений NMR и GPC; затем Mn и дисперсность Đ.
- Частично измеренные свойства потребуют изменения текущего контракта API.

Monash ещё не загружен в MVP. Временные точки одной кинетической кривой нельзя считать независимыми синтезами. CT/CM — отношение агента переноса цепи к мономеру; это не доля инициатора.

**Критерии готовности:**
- В ETL каждая итоговая запись прослеживается до исходного файла и experiment_id.
- Разбиение train/test не разделяет одну кинетическую кривую между выборками.
- Отчёт импорта показывает число принятых и исключённых записей с причинами.

## Схема и качество

Статус по карте: описано как реализованное

Единый контракт удерживает параметры, свойства и ограничения согласованными на всех этапах. Проверки ловят структурные и численные ошибки до того, как они попадут в историю или обучение; химический смысл данных требует отдельного протокола.

**Описанные функции:**
- Pydantic запрещает лишние поля, NaN и бесконечность.
- Имена факторов и свойств уникальны, не конфликтуют со служебными полями CSV.
- От 1 до 12 факторов; от 1 до 8 свойств; до 30 линейных ограничений.
- Нижняя граница фактора строго меньше верхней; у свойства задана хотя бы одна целевая граница.
- Для completed нужны все измерения; failed не может иметь роль calibration.

**Следующие задачи:**
- Проверка единиц измерения и преобразование единиц.
- Контроль происхождения, дубликатов и групп экспериментов.
- Метки качества, протоколы измерения и причины неуспеха.



**Критерии готовности:**
- Единицы каждого значения однозначно заданы и преобразуются по проверяемым правилам.
- Частичные измерения имеют явный статус, не маскируются нулями и не попадают в неверную модель.

## API и состояние

Статус по карте: описано как реализованное

Сервис хранит согласованную версию проекта и обслуживает интерфейс через HTTP API. Для небольшого локального MVP выбран SQLite с одним документом состояния: это простая проверяемая основа для цикла, а не готовая многопользовательская LIMS.

**Описанные функции:**
- В SQLite хранится один сериализованный JSON-документ состояния проекта.
- RLock и транзакция обеспечивают атомарное обновление в рамках локального процесса.
- Сохраняются configuration, trials, recommendations, model metadata, acquisition, revision.
- Рекомендации содержат ID обучающих опытов.
- Снимок переживает перезапуск приложения.

**Следующие задачи:**
- Нормализованная схема БД для кампаний, измерений, версий моделей и пользователей.
- Версионирование артефактов моделей и данных.
- Авторизация, права и промышленный аудит.

Фактические обученные GP не сериализуются в БД: model — метаданные. При каждом запросе рекомендаций обучение запускается заново.

**Критерии готовности:**
- Любая рекомендация восстанавливается по версии кода, конфигурации и точному набору обучающих данных.
- Перезапуск сохраняет историю и статусы опытов; резервная копия проверена восстановлением.

## Прогноз свойств

Статус по карте: описано как реализованное

Модель отвечает на вопрос: какие свойства можно ожидать при заданных параметрах опыта и насколько неопределён этот прогноз? В v0.1 каждое свойство имеет свой независимый Gaussian Process; выбор следующего эксперимента выполняет отдельный модуль.

**Описанные функции:**
- sklearn GaussianProcessRegressor.
- Ядро ConstantKernel × Matérn 5/2 + WhiteKernel; отдельная длина шкалы по каждому фактору.
- normalize_y=True; alpha=1e-8 для численной устойчивости.
- Гиперпараметры подбирает L-BFGS-B с ограничением 60 итераций.
- Для обучения требуется минимум 3 различные завершённые train-точки.
- Если данных меньше, применяется начальный план без выдуманных прогнозов.

**Следующие задачи:**
- Ridge и CatBoostRegressor как честные сравнительные модели.
- BoTorch SingleTaskGP / ModelListGP для раздельно измеренных свойств.
- Раздельное представление неопределённости функции и шума наблюдений.

Ни CatBoost, ни BoTorch пока не установлены и не обучены в MVP. 3 точки — технический минимум запуска, не доказательство качества.

**Критерии готовности:**
- GP, Ridge и CatBoost сравнены на одинаковых независимых группах и одном протоколе препроцессинга.
- Для каждого свойства есть MAE/RMSE и график ошибки по области факторов.
- При частичных выходах модель использует только фактически измеренные значения соответствующего свойства.

## Неопределённость

Статус по карте: описано как реализованное

Интервал должен отражать неопределённость прогноза и явно сообщать, чем он обоснован. Текущая реализация умеет расширять или сужать интервалы по отдельной калибровочной выборке, но не выдаёт это за доказанную вероятность успеха на новой установке.

**Описанные функции:**
- Калибровочные outcomes не участвуют в обучении GP, выборе лучшего опыта и acquisition.
- Оценка невязки |y − μ| / σ на калибровочной выборке.
- Порядковая статистика с рангом ceil((n + 1) × confidence), без интерполяции.
- При недостатке данных возвращается явно некалиброванный GP-интервал.
- Совместная вероятность попадания всех свойств всегда помечена probability_calibrated=false.

**Следующие задачи:**
- Протокол независимой калибровки для выбранного типа опыта.
- Проверка фактического покрытия и ширины интервалов на новых группах.
- Групповая или иерархическая калибровка для кинетических кривых.

Заявляется только маргинальное покрытие отдельного свойства при обменности данных. Не заявлены совместное покрытие и гарантия для адаптивно выбранных кандидатов. В текущем коде совпадающие по X train/calibration-точки исключаются из калибровки.

**Критерии готовности:**
- Протокол определяет независимую экспериментальную единицу и способ выделения калибровки.
- На отложенных группах измерены покрытие и средняя ширина интервалов.
- Совместная вероятность и маргинальные интервалы имеют разные явные подписи в интерфейсе.

## Выбор следующего опыта

Статус по карте: описано как реализованное

Этот модуль превращает прогноз модели в решение, какой опыт проводить следующим. Он сопоставляет вероятное приближение к целевым свойствам с неопределённостью и возвращает конкретный набор допустимых параметров.

**Описанные функции:**
- Потеря — среднее нормированное отклонение свойств за границы целевых диапазонов.
- До первого попадания максимизируется Monte Carlo expected improvement этой потери.
- После первого измеренного попадания выбирается высокая модельная вероятность повторного попадания.
- По умолчанию 128 MC-выборок и до 1536 точек-кандидатов.
- Несколько кандидатов выбираются жадно со штрафом за близость.

**Следующие задачи:**
- BoTorch qLogNEI для более устойчивой работы с шумом.
- Учёт стоимости и времени синтеза, очереди ещё не завершённых опытов.
- Стратегия подтверждающих повторов и критерий остановки кампании.

Текущая серия — эвристика разнообразия, не точный совместный q-EI. qLogNEI пока только запланирован. Несколько целевых диапазонов сами по себе не означают необходимость Pareto-оптимизации.

**Критерии готовности:**
- Офлайн-выбор не получает скрытые результаты до запроса соответствующего кандидата.
- Все методы сравниваются при одном бюджете, включая начальный план и подтверждения.
- Причина выбора воспроизводится по сохранённым параметрам acquisition и истории.

## Допустимая область

Статус по карте: описано как реализованное

Поиск проходит только внутри явно заданного пространства параметров. Этот слой отвечает за математическую допустимость кандидатов: технологические правила и возможность выполнения конкретного режима задаёт специалист по установке.

**Описанные функции:**
- scipy.optimize.linprog проверяет существование допустимой области.
- Глобальные кандидаты Latin Hypercube дополняются локальными точками около лучших результатов.
- Для узких многогранников используются выпуклые комбинации вершин и hit-and-run.
- Отбрасываются уже выполненные train/calibration/failed-точки.
- Финальные параметры повторно проверяются перед выдачей.

**Следующие задачи:**
- Управляемые категориальные факторы.
- Согласованные с технологом нелинейные правила и ограничения установки.
- Осознанные повторные измерения для оценки шума.

Выполнение математических ограничений не является доказательством безопасности химического режима.

**Критерии готовности:**
- Каждое правило установки согласовано и имеет проверяемую реализацию.
- Категориальные значения выбираются из разрешённого перечня, а не кодируются произвольными непрерывными числами.
- Подтверждающие повторы разрешаются явно и входят в бюджет кампании.

## Проведение опыта

Статус по карте: частично

Параметры кандидата превращаются в проведённый опыт и измеренный результат. В MVP этот переход реализован искусственным симулятором или ручным внесением; аппаратная связь с реальной пилотной установкой ещё отсутствует.

**Описанные функции:**
- В demo результат выдаёт воспроизводимая искусственная функция от трёх факторов A/B/C.
- В real симулятор отключён; пользователь вносит результаты вручную или через CSV.
- Результат с recommendation_id должен соответствовать параметрам актуальной рекомендации.
- Устаревший ID возвращает ошибку 409.

**Следующие задачи:**
- Проверка и утверждение плана технологом.
- Интеграция с LIMS/историей установки по согласованному интерфейсу.
- Операционные статусы planned / running / measured / rejected.
- Аппаратная интеграция только после согласования протокола установки.

Нет подключения к физическому оборудованию. Симулятор — не химическая модель, названия свойств учебные.

**Критерии готовности:**
- Для каждого выполненного опыта сохранены утверждённые и фактические параметры.
- Повторная доставка результата не создаёт дубликат опыта.
- Адаптер установки проверен сначала на согласованной имитации обмена, затем в наблюдаемом пилоте.

## Измерение и переобучение

Статус по карте: описано как реализованное

После каждого измерения платформа обновляет знания и готовит следующий шаг. Обновление истории, сброс устаревших рекомендаций и новое обучение образуют закрытый программный цикл.

**Описанные функции:**
- append_trial добавляет опыт с внутренним ID и UTC-временем.
- invalidate удаляет прежние рекомендации и метаданные модели после добавления результата.
- Следующий POST /api/recommend повторно обучает GP на обновлённой train-истории.
- В демонстрационном интерфейсе после симуляции автоматически запрашивается новая рекомендация.

**Следующие задачи:**
- Асинхронные измерения и разные задержки NMR/GPC.
- Неизменяемая связь сырого файла измерения, опыта и версии модели.
- Контроль сдвига данных и повторного обучения по событиям.

Автоматическое переобучение происходит на следующем запросе рекомендаций, а не в фоне сразу после записи измерения.

**Критерии готовности:**
- Позднее измерение дополняет нужный опыт, сохраняя источник и время получения.
- Каждая новая версия модели фиксирует точный состав доступных на тот момент наблюдений.
- Старые рекомендации нельзя выполнить повторно через устаревший ID.

## Проверка качества

Статус по карте: частично

Проверка разделяет три вопроса: корректно ли работает код, насколько точно модель предсказывает свойства и сокращает ли последовательный выбор число реальных опытов. Сейчас доказана работа программного цикла и получен результат на одной искусственной задаче.

**Описанные функции:**
- 18 unittest проверяют ограничения, импорт, сохранение, отсутствие утечки calibration и API-сценарии.
- Сохранён benchmark на 20 seed: 24 опыта, первые 8 общие; GP, random и LHS.
- GP достиг цели 20/20; random 1/20; LHS 0/20 на одной искусственной функции.
- Неудачные запуски не исключаются; время достижения цели учитывает цензурирование.

**Следующие задачи:**
- GroupKFold по независимым экспериментам; метрики MAE/RMSE на свойствах.
- Архивная оптимизация только по конечному пулу реально измеренных кандидатов со скрытыми метками.
- Калибровка и повторы включаются в бюджет.
- Проспективное сравнение с базовым методом на установке заказчика.

Результат синтетического benchmark не доказывает экономию реальных синтезов. Ни 50–70%, ни 10–25× для нашего прототипа не подтверждены.

**Критерии готовности:**
- В отчёте есть все seed/серии, включая недостигшие цели в бюджете.
- Заранее зафиксирован независимый split и алгоритм не видит скрытые ответы.
- Синтетический, архивный и проспективный результаты опубликованы раздельно с ограничениями вывода.

## Запуск и интерфейс

Статус по карте: описано как реализованное

Прототип запускается на обычном CPU как локальное веб-приложение и не зависит от облачного LLM. Интерфейс служит для задания задачи, просмотра следующего опыта, загрузки измерений и проверки состояния модели.

**Описанные функции:**
- FastAPI + Uvicorn, HTML/CSS/JavaScript без CDN.
- Четыре экрана: следующий опыт, данные, проверка качества, настройки.
- По умолчанию приложение слушает только 127.0.0.1.
- Порт: POLYMER_LAB_PORT; база: POLYMER_LAB_DB.
- После установки зависимостей не нужны интернет, GPU и облачный LLM.

**Следующие задачи:**
- Развёртывание внутри контура заказчика.
- Управление пользователями, резервные копии и мониторинг.
- Упаковка и воспроизводимые версии зависимостей.

Это однопользовательский прототип. Визуальная браузерная проверка MVP ранее была ограничена средой; функциональные API-тесты пройдены.

**Критерии готовности:**
- Развёртывание воспроизводится из зафиксированных версий зависимостей.
- Права доступа соответствуют ролям исследователя, технолога и администратора.
- Проверены резервное восстановление и наблюдаемость ошибок сервиса.

## Следующий спринт

Статус по карте: запланировано

Ближайшая задача — получить первое проверяемое качество на реальных открытых данных, сохранив узкую постановку. Стартуем с одного мономера и конверсии, затем добавим молярную массу, дисперсность и данные конкретной установки.



**Следующие задачи:**
- Согласовать один мономер и экспериментальный endpoint; сначала прогноз конверсии.
- Сохранить raw-файлы и построить таблицу с experiment_id, единицами и статусами.
- Сравнить Ridge, CatBoost и GP по группам экспериментов.
- Добавить поддержку разных наблюдаемых выходов и ModelListGP при необходимости.
- Сравнить последовательный выбор с random / DoE по скрытому конечному пулу.
- Добавить независимую калибровку и стоимость опытов.
- Получить архив заказчика и согласовать проспективный пилот.

Это план разработки. Реальные датасеты и дополнительные модели ещё не интегрированы.

**Критерии готовности:**
- Обработанный Monash-набор имеет происхождение, лицензию, единицы и независимые группы.
- Есть воспроизводимый отчёт сравнения трёх моделей и конечного пула BO.
- Следующий пилот имеет согласованные baseline, бюджет, критерий успеха и порядок подтверждения результата.
